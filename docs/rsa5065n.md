# RSA5065N and LibreCAL command notes

What wheecal sends to each instrument, where each command came from, and what is verified.

## Rigol RSA5065N, VNA option (driver `rsa5065n`)

**Sources.** The commands come from the instrument itself:
- its SCPI command tree;
- its built-in help, which maps each command to the panel button it equals;
- the RSA5000 VNA user guide.

**Checked live** (queries only) on firmware 00.03.08: `*IDN?`, `:INST:SEL?`, `:CONF?`, the kit fields, the
calibration state queries, `:SWEep:TIME?` and `:TRACe1:DATA?`. **Not run live:** the calibration steps. See [Verified so far](#verified-so-far).

The `[:SENSe]` prefix shown in the help gets no reply; the bare `:CALibration:…` form works.

### Custom cal kit

| Command | Meaning |
|---|---|
| `:CALibration:CKIT:TYPE OPEN\|SHORt\|LOAD\|THRough` | which standard the fields edit. `TYPE?` answers `OPEN\|SHOR\|LOAD\|THRU`. |
| `:CALibration:CKIT:LENGth` | offset length, meters (the screen shows mm) |
| `:CALibration:CKIT:Z0` | R, ohms (load) |
| `:CALibration:CKIT:LOSS` | "Att", a flat loss in dB (wheecal writes 0) |
| `:CALibration:CKIT:C0..C3` | open capacitance, fF, fF/GHz, fF/GHz², fF/GHz³ |
| `:CALibration:CKIT:L0..L3` | short inductance, pH, pH/GHz, pH/GHz², pH/GHz³ |
| `:CALibration:CKIT:LABel CUSTom` | select the Custom kit (`LABel?` answers `CUST`) |

- **One open and one short.** The Custom kit holds one open (C0..C3) and one short (L0..L3); all standards share
  them.
- **Editable fields:**

  | Standard | Fields |
  |---|---|
  | Open | length, C, Att |
  | Short | length, L, Att |
  | Load | R, Att |
  | Through | length, Att |

  Querying a greyed field returns garbage (`LOAD` `LENGth?` gives L3/1000), so wheecal never writes or checks those.
- **Dropped writes.** A setting sent while the instrument is busy is dropped without an error. So every write is
  followed by `*OPC?`, and every kit field is read back and re-sent up to 3 times.
- **No kit name.** The kit name can't be set over SCPI.

### S11 calibration (1-port)

Panel: *S11 Meas Setup › Align*. The menu has exactly Open, Short, Load, Abort and Done.

| Command | Panel |
|---|---|
| `:CALibration:S11:OPEN` / `:SHORt` / `:LOAD` | Align › Open / Short / Load |
| `:CALibration:S11:SAVE` | Align › Done ("the calibration results are saved") |
| `:CALibration:S11:ABORt` | Align › Abort |
| `:CALibration:S11:STATe?` | 0/1, "calibration on": **not trustworthy**, see below |

### S21 calibration (2-port through)

Panel: *S21 Meas Setup › Align*. The menu has Through, Abort and Done. The user guide says: "the calibration
coefficients are measured by connecting the Through to the two test ports. This calibration effectively eliminates
the transmission tracking error".

| Command | Panel |
|---|---|
| `:CALibration:S21:THROugh` | Align › Through |
| `:CALibration:S21:SAVE` | Align › Done |
| `:CALibration:S21:ABORt` | Align › Abort |
| `:CALibration:S21:STATe?` | 0/1, "calibration on": **not trustworthy**, see below |
| `:CALibration:S21:NORState?` | a state query (reads 0); not a step |

**There is no isolation, load or match step.** The firmware's `:CALibration:S21` subtree has only `THROugh`,
`ABORt`, `SAVE`, `STATe`/`STATe?` and `NORState?`. Live queries of `:CAL:S21:ISOL?`, `:MATC?` and `:LOAD?` get no
reply, and `:SYST:ERR?` then reports `match fail` (no such command).

wheecal's automatic S21 sequence:
1. `*IDN?`, `:INST:SEL?` (must be `VNA`), `:CONF?` (must be `S21`; wheecal never changes it)
2. Optional kit check: read the Custom kit's Through length back and compare it with the LibreCAL fit.
3. LibreCAL `:PORT <a> THROUGH <b>`, then `:PORT? <a>` reads `THROUGH <b>`.
4. `:CALibration:S21:THROugh`, then `*OPC?` and the settle time.
5. `:CALibration:S21:SAVE`. `:CALibration:S21:STATe?` is polled for 3 s and logged (advisory only).
6. Screenshot `:PRIV:SNAP?`: the correction badge decides (see below). Nothing is aborted after `SAVE`.
7. LibreCAL `:PORT 1..4 NONE`. After a failure **before** `SAVE`, or on Cancel, `:CALibration:S21:ABORt` is sent
   first.

### STATe? reads 0 with a correction on

On firmware 00.03.08, `:CALibration:S11:STATe?` (and `:STAT?`) reads **0 while a correction is active**. On
2026-11-25 the panel showed "C ?" while it read 0. On 2026-11-26 it showed "Cor" while `:STAT?` and `:STATe?` both
read 0. Other queries get no reply at all: `:CAL:S11:NORState?`/`:NORS?`, `:CALC:CORR:STAT?` and
`:SENS:CORR:STAT?`. **No SCPI query tells whether a correction is on.**

**`ABORt` after `SAVE` discards the calibration.** wheecal 0.1.0 aborted when `STATe?` read 0 after Done, and so
threw away a calibration that had applied. Since 0.1.1, `ABORt` is sent only:
- on Cancel, or an error before `SAVE`;
- when the user asks to discard: GUI **Abort / discard**, or `wheecal --discard-cal s11|s21`.

### The correction badge (how wheecal verifies)

The screen has a badge at the top left of the 1024×600 screenshot, between the logo and "TG on":
- box x 253-297, y 4-27
- fill RGB (50, 50, 50), border (66, 66, 66)

| Badge | Text | Meaning | wheecal |
|---|---|---|---|
| `---` | grey (≈121,121,130), two rows of dashes | no correction | not applied (the cal is still left in place) |
| `Cor` | blue (≈18,137,176) | correction on | applied |
| `C ?` | blue (≈3,180,239) | on, interpolated / other conditions | applied (interpolated) |
| `C !` | not captured yet | on, with a warning | applied (any clear mark that is not blank) |

`wheecal/screen.py` classifies the badge in four steps:
1. **Is the box there?** At least 55 % of its inside must be the fill colour. Otherwise the result is *unknown*.
2. **Count differing pixels.** Compare against each reference: `---`, `Cor`, `C ?`. A pixel differs when a channel
   is off by more than 30. Shifts of ±1 px are tried and the best match kept.
3. **Match a reference.** At most 4 differing pixels matches the blank; at most 6 matches `Cor` or `C ?`.
4. **Any other mark counts as on.** At least 20 pixels that differ from the blank, over at least 5 rows, mean
   *on*. Anything else is *unknown*, and wheecal says to check the screen.

On the real captures each state differs from the other references by 59-124 pixels, so there is a wide margin.

The references are crops of real screenshots of this instrument (`wheecal/drivers/rsa5065n_badge.py`):
- blank: no calibration, 2026-11-25
- "C ?": live, 2026-11-25
- "Cor": live, 2026-11-26

**Not captured yet:** `C !`, and screens with a dialog over the badge. Those classify as *on* (a clear mark) or
*unknown*. Each run saves its crop to `<settings dir>/indicator/`.

**The through length.** wheecal fits the LibreCAL through's electrical length and writes it as the kit's Through
length:
1. Read `P<ab>_THROUGH` from the LibreCAL.
2. Unwrap the phase of S21 and fit a straight line: phase = φ0 − 2πfτ.
3. Length = c·τ (in air).

Whether the RSA5065N's through calibration uses that length or only normalizes isn't documented. Check it on the
bench, as described in the [user guide](user-guide.md#after-calibrating).

### Sweep time: *OPC? does not wait for a sweep

The sweep time scales with the number of points and the IF bandwidth: about **4.5 s at 1000 points**.
`:SWEep:TIME?` answers it in seconds. **`*OPC?` does not wait for a sweep** on firmware 00.03.08: it answers in about
0.2 s while a sweep runs. So waiting has to be by time.

Measured on 2026-11-26 at 4.5 s per sweep, switching the LibreCAL from Open to Short: the trace still showed the
open right after the switch, was half changed at +2.8 s and settled only by about +5.6 s, more than one sweep.

wheecal 0.1.1 waited a fixed 0.5 s after each LibreCAL switch and 3 s after each measure command, both shorter than
one sweep. Each standard was then captured as a blend with the one before it, the error terms were wrong, and after
Done S11 read well above 0 dB.

Since 0.1.2, wheecal reads `:SWEep:TIME?` and waits **2 × sweep time + 1 s** (never less than the configured settle
times) on both sides of each cal step: after switching the LibreCAL, before the measure command, and after it. On
the bench this gave a clean calibration: Open mean 0.00 dB, Short -0.02 dB, Load -24 dB, badge "Cor". When
`:SWEep:TIME?` can't be read, the configured settle times are used.

### Reading the trace

`:TRACe1:DATA?` returns the S11 trace as ASCII pairs `(re,im)(re,im)...` (`:FORMat:DATA` is `ASC,8`).
`:TRACe:DATA? TRACE1` answers `error`. wheecal reads the trace for `--verify-standards` (read only; it sends no
writes) and for the host-side calibration.

### Host-side calibration (0.2.0)

`--host-cal` needs the raw trace, so it sends `:CALibration:S11:ABORt` (and warns) before reading. `:TRACe1:DATA?`
then returns uncorrected S11. The sweep frequencies are `:FREQ:STAR?` .. `:FREQ:STOP?` in `:SWEep:POINts?` equal
steps (`sweep_freqs()`). This assumes a linear sweep, which the bench check confirms. The correction is applied in
wheecal only, so the screen keeps showing the raw trace.

Bench (firmware 00.03.08, 100 kHz-3 GHz, 1000 points, 4.5 s per sweep): the independent through check reads a mean
|error| of 0.062 and a max of 0.107. On-board calibrations of the same through: the ideal kit
(`6650F03E-M`) reads 0.109 / 0.232, and the fitted LibreCAL kit 0.146 / 7.32 (|S11| up to +17 dB). Details in
[host-calibration.md](host-calibration.md).

### Writes wheecal allows

The allowed prefixes are:
- `:CALibration:CKIT:`
- `:CALibration:S11:OPEN|SHORt|LOAD|SAVE|ABORt`
- `:CALibration:S21:THROugh|SAVE|ABORt`

Anything else raises an error before it is sent. Tests cover span, points, IF bandwidth, source power, `*RST`,
preset, `:CALibration:CLEAr`, mode and measurement.

### Verified so far

- **Checked live:** the queries above, and kit writes with read-back.
- **Run by the owner (v0.1.0, 2026-11-25):** an automatic S11 calibration. `OPEN`/`SHORt`/`LOAD`/`SAVE` ran. Then
  `STATe?` read 0 and v0.1.0 sent `ABORt` (fixed in 0.1.1, above).
  - **Asynchronous measurements.** The measure commands start an asynchronous measurement (the screen shows
    "Open Calibrating…"), so wheecal waits *settle* seconds after `*OPC?`.
  - **Frequency range.** The instrument sweeps to 6.5 GHz, while the LibreCAL data goes higher. wheecal 0.1.1 fits
    over the sweep, never above 6.5 GHz. A fit to 8.5 GHz gave an open worst error of +5.3 dB.

## LibreCAL

The commands come from [jankae/LibreCAL](https://github.com/jankae/LibreCAL): `Documentation/SCPI_API.tex` and
`Software/LibreCAL/src/SCPI.cpp`. USB VID:PID is 1209:4122, a CDC serial port. Every command answers one
CRLF-terminated line: empty on success, `ERROR…` on failure. Standard names are case sensitive.

| Command | Use |
|---|---|
| `*IDN?` | `LibreCAL,LibreCAL,<serial>,<firmware>` |
| `:PORTS?` | number of ports (4) |
| `:PORT <p> OPEN\|SHORT\|LOAD\|NONE` | set a port's standard |
| `:PORT <p> THROUGH <q>` | connect ports p and q (both are set) |
| `:PORT? <p>` | read a port's state back |
| `:TEMPerature?`, `:TEMPerature:STABLE?` | temperature, and whether it is stable |
| `:COEFFicient:LIST?` | coefficient sets (`FACTORY` first) |
| `:COEFFicient:NUMber? <set> <name>` | points in a coefficient (`P1_OPEN` … `P34_THROUGH`) |
| `:COEFFicient:GET? <set> <name> <i>` | `f_GHz,re,im` (reflection) or S11,S21,S12,S22 (through) |

wheecal never sends the commands that write the LibreCAL's memory or settings: `:COEFFicient:CREATE`, `ADD`,
`DELete` and `FINish`, `:FACTory:*`, `:BOOTloader`, `:TEMPerature <value>`.

**Not checked against a LibreCAL** by this project yet. A simulated LibreCAL that mirrors `SCPI.cpp`'s replies is
used in the tests.
